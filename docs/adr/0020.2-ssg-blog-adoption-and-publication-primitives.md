# 0020.2. SSG Blog Adoption And Publication Primitives

**Date**: 2026-04-19
**Status**: Proposed
**Depends on**: [0020.1-static-site-generation-build-toolkit](./0020.1-static-publication-components-and-attributes.md)

## Context

ADR 0020.1 split SSG into a dedicated `@nisli/ssg` package and made
`buildStaticSite()` the public entry point. The package currently provides a
small build spine:

- clean output directory
- copy public assets
- write route output to `dist/<route>/index.html`
- pass a typed build context to route render functions
- run `beforeBuild`, `onPage`, and `afterBuild` hooks

The publication site still owns most of the real SSG pipeline in
`/Users/goga/Documents/goga/blog/packages/blog/src/pipeline/build.ts` and
`/Users/goga/Documents/goga/blog/packages/blog/src/lib/fs.ts`.

The next phase is to move reusable build mechanics into `@nisli/ssg` without
moving blog-specific editorial policy into the framework.

## Decision

Start with the generic filesystem/build spine needed by the blog:

- `cleanOutDir(outDir)`
- `copyPublicAssets({ publicDir, outDir })`
- `routeToFilePath(outDir, routePath)`
- `writeRoute(outDir, routePath, html)`
- `writeRoot(outDir, filename, content)`

Then make `buildStaticSite()` use those primitives internally.

These helpers are public because they let the blog adopt `@nisli/ssg`
incrementally. The blog does not need to move its entire pipeline at once. It can
first replace generic output helpers while keeping its own content discovery,
frontmatter schema, page templates, feeds, sitemap, OG images, and `llms.txt`
policy.

## Engineering Slice 1

Phase 2A starts with the output spine:

1. Add reusable output helpers to `@nisli/ssg`.
2. Export those helpers from the package barrel.
3. Refactor `buildStaticSite()` to call those helpers.
4. Add tests for route mapping, root file writing, path traversal rejection,
   output cleaning, and public asset copying.
5. Update `@nisli/ssg` documentation.
6. Bump `@nisli/ssg` for the new API surface.

This is deliberately smaller than moving Markdown, feeds, sitemap, or component
serialization. The goal is to prove the package boundary against the blog's
existing pipeline before turning publication policy into framework API.

Implementation checkpoint:

- `packages/ssg/src/output.ts` owns the reusable output helpers.
- `packages/ssg/src/build.ts` uses `cleanOutDir()`, `copyPublicAssets()`, and
  `writeRoute()` internally.
- `packages/ssg/src/index.ts` exports the output helpers and their small option
  types.
- `packages/ssg/src/output.test.ts` covers route mapping, root file output,
  traversal rejection, cleaning, and asset copying.
- `packages/ssg/src/build.test.ts` confirms `buildStaticSite()` still writes
  routes, preserves output when `clean: false`, copies assets, rejects dynamic
  routes, and runs hooks.
- `packages/ssg/README.md` documents the output helpers and route mapping.
- `@nisli/ssg` is bumped to `0.2.0` for this public helper surface.

## Public API Direction

The first reusable surface:

```ts
import {
  buildStaticSite,
  cleanOutDir,
  copyPublicAssets,
  writeRoot,
  writeRoute,
} from '@nisli/ssg';

cleanOutDir('dist');
copyPublicAssets({ publicDir: 'public', outDir: 'dist' });
writeRoute('dist', 'about', '<main>About</main>');
writeRoot('dist', 'feed.xml', feedXml);
```

The higher-level build API remains:

```ts
await buildStaticSite({
  outDir: 'dist',
  publicDir: 'public',
  routes: [
    { path: '/', render: () => '<main>Home</main>' },
    { path: '/about', render: () => '<main>About</main>' },
  ],
});
```

## Blog Adoption Plan

Phase 2A should let the blog replace:

- `writeOutput(slug, html)`
- `writeRoot(filename, content)`
- `copyAssets()`
- `cleanDist()`

with `@nisli/ssg` helpers.

The blog should keep:

- `discoverPosts()`
- frontmatter parsing and validation
- Markdown rendering
- TypeScript article module loading
- page shell rendering
- post templates
- section archive templates
- JSON-LD
- RSS
- sitemap
- `llms.txt`
- OG image generation
- client bundling

Success criteria:

- blog depends on `@nisli/ssg`
- blog build uses `@nisli/ssg` for generic output mechanics
- `pnpm -C packages/blog typecheck` passes
- `pnpm -C packages/blog build` passes
- output remains equivalent for representative routes and root files

The immediate next repository to change is the blog, not Nisli itself. The blog
should replace only generic filesystem helpers first. Its content model and
publication policy should remain local until at least one more publication
shape proves the same abstraction.

## Later Phases

### Phase 2B: Publication Primitives Behind Hooks

Add reusable helpers only after the blog and another site prove the abstraction:

- route manifest expansion
- canonical URL helpers
- sitemap helper
- RSS helper
- JSON file helper
- typed publication metadata helpers

These must be data-driven and hook-based. They should not assume the blog's
exact frontmatter schema.

Candidate API shape:

```ts
await buildStaticSite({
  outDir: 'dist',
  publicDir: 'public',
  routes,
  afterBuild: async result => {
    writeRoot(result.outDir, 'sitemap.xml', renderSitemap({ pages: result.pages }));
    writeRoot(result.outDir, 'feed.xml', renderFeed(feedData));
  },
});
```

### Phase 2C: Component-Aware Internal Rendering

Build the internal component serializer needed for true Nisli SSG:

- serialize existing `html` templates
- render normal `component()` factory results
- evaluate signal/computed values once
- serialize `class:name`, attributes, arrays, conditionals, and `html:inner`
- omit or reject browser-only events, refs, lifecycle hooks, effects, and host
  mutation
- keep the customer-facing API as `buildStaticSite()`

### Phase 2D: Island Asset Coordination

Add a route/page-level way to collect or declare client bundles needed by custom
element islands.

This is progressive enhancement, not hydration.

### Phase 2E: Publishing Hardening

Make package publishing boring:

- confirm `@nisli/ssg` exists on npm (`0.1.0` is published; `0.2.0` is the
  next unpublished helper release)
- configure npm Trusted Publisher for `@nisli/ssg`
- verify the matrix workflow publishes future `@nisli/ssg` versions
- keep `@nisli/core` and `@nisli/ssg` versions independent
- clean up failed release/tag state only when retrying the same version

## Non-Goals

This slice does not include:

- moving the whole blog build into `@nisli/ssg`
- Markdown/frontmatter parsing
- feed generation
- sitemap generation
- JSON-LD generation
- OG image generation
- client bundling
- component-aware rendering
- hydration or request-time SSR
