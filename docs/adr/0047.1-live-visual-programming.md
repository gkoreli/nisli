# 0047.1. Live Visual Programming — The Rendered Interface Is the Source Code

**Date**: 2026-08-31
**Status**: Proposed
**Supersedes**: [0047](./0047-visual-programs-as-source.md)
**Depends on**: [0034](./0034-engine-typed-blocks-decided-by-an-engine.md), [0041](./0041-engine-proof-domain.md), [0046](./0046-engine-density-and-input-axes.md)
**Executable evidence**: [Import transactions `.nvis`](../research/visual-programming/examples/import-transactions/README.md)

## Context

ADR 0047 assumed a visual program would be compiled into typed Engine block
calls. That retained the old architecture unnecessarily: the visual was still
an intermediate representation on its way to the “real” textual UI program.

The stronger model has no UI compilation boundary. An agent works on a running
visual world, and that same persistent object is what the application executes.
HTML, Canvas, WebGPU, native controls, and accessibility trees are rendering
backends—not application source formats.

## Decision

Pursue Nisli as a live visual programming environment in which the rendered
interface is the source code.

```text
look → paint → bind → interact → observe → revise
```

There is no JSX, block-call authoring, generated application TypeScript, or
visual-to-code round trip in this model.

This does not mean authors paint and retain a complete scene graph by hand. A
full list of marks, coordinates, and materials would be markup regardless of
whether it is serialized as text or binary. The target authoring source is
sparse: accepted observations and visual corrections over Engine policy. The
retained visual graph is runtime state and projection machinery.

### 1. `.nvis` is an executable visual program

A saved visual program carries:

- **observations** indexed by application state and environmental context;
- **identity** connecting the same visible thing across observations;
- **continuity** describing persistence, reflow, replacement, appearance,
  folding, and other changes between observations;
- **semantic ports** connecting visible things to domain values, collections,
  and effects;
- **visual material** including text, surfaces, controls, strokes, imagery, and
  arbitrary painted residuals;
- **edit history** recording paint, bind, propagate, observe, and revision
  operations.

The object is code because the runtime evaluates it:

```text
visual program × context × application state × data → interactive surface
```

These records are runtime memory, not an author-facing textual syntax. Agents
and people manipulate the projected visual world.

### 2. The runtime interprets; it does not generate application code

The visual runtime selects and evaluates observations, preserves identities,
applies continuity, substitutes bound values, repeats visual patterns over
collections, performs hit testing, and sends interaction through semantic
ports. A renderer projects that evaluation to the current platform.

A renderer may create DOM nodes or GPU commands. That is backend machinery,
analogous to a browser painting HTML or a game engine submitting a scene to the
GPU. No generated DOM or TypeScript becomes a second source of truth.

### 3. TypeScript is the domain boundary

CSV parsing, banking rules, persistence, networking, and other domain services
may remain TypeScript. They bind to the visual program's typed port surface:

```ts
visual.bind({
  file,
  account,
  previewRows,
  importAction: importTransactions,
});
```

This code supplies values and effects. It does not describe layout,
appearance, component structure, responsiveness, or interaction presentation.
The port manifest can produce development-time type declarations without
generating UI implementation.

### 4. Engine becomes visual-machine policy

The durable work in `@nisli/engine` remains useful beneath the visual runtime:
fit, input and density axes, overlays, focus, native controls, accessibility,
waiting, and verification. Its current application-facing block vocabulary is
not assumed to be the final visual-language surface.

The runtime owns deterministic policy whenever a visual observation leaves a
choice unresolved. The visual object owns choices the agent explicitly made.

### 5. Rendering must retain platform semantics

The first executable example uses Canvas to prove direct interpretation. That
is not the final accessibility architecture. A production renderer projects
semantic ports to native text and controls, exposes names/states/actions to the
accessibility tree, and uses Canvas/WebGPU only for irreducible visual material.

The visual program remains authoritative even when its projection is hybrid.

### 6. Training is not an MVP dependency

The file format, runtime, observation selection, identity, continuity, binding,
and direct manipulation can all be deterministic. Existing multimodal models
may operate the visual editor, but no custom model is required to define or
execute the language.

Training is reconsidered only if it materially improves visual suggestion,
local edit propagation, or extrapolation. It is not part of the language's
foundation.

## Executable example

The first `.nvis` artifact is a 16,054-byte checksummed binary visual program
for Ledger's Import transactions flow. It contains four observations:

```text
empty @ wide       populated @ wide
empty @ narrow     populated @ narrow
```

The generic runtime reads the binary directly. State chooses observations;
width chooses a saved topology; identities survive both changes; data fills
visual text and repeated rows; clicking visual controls returns semantic ports
to domain code. No screen implementation is emitted.

The construction fixture is intentionally separate and never imported by the
runtime. It stands in for the future paint editor and demonstrates that the
`.nvis` artifact—not its creation tooling—is the application UI source.

## MVP sequence

1. **Executable object** — binary envelope, observations, identities,
   continuity, ports, materials, edits, one direct renderer. Proven by the
   example.
2. **Live editor** — select, paint, bind, propagate, undo, and save operate on
   the running object.
3. **Native semantic projection** — text, controls, collections, focus, and the
   accessibility tree are projected without changing the source model.
4. **Reactive domain binding** — typed port adapter for core signals, actions,
   resources, and collections.
5. **Visual proof** — evaluate every declared observation and continuity edge;
   test names, reachability, fit, state coverage, and edit locality.
6. **Application dogfood** — run one Ledger screen from `.nvis` with no block
   implementation beside it.

## Consequences

**Positive.** Nisli has a genuinely post-textual UI model. Generated code
quality and textual tree ergonomics stop constraining visual authoring. The
running interface, saved program, and editing target are one object.

**Negative.** Nisli must build an editor, runtime, semantic projection,
debugger, diff model, and new verification domain. Browser-native behavior can
no longer be inherited accidentally; it must be projected deliberately.

**Risk.** If authoring exposes marks, coordinates, continuity records, or ports
as a textual schema, the project has merely invented another UI DSL. Those are
internal runtime concepts. The public authoring test is whether the loop remains
look → paint → bind → interact → observe → revise.
