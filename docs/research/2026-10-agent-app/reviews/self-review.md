# Adversarial self-review

Same investigator; this is not an independent review or agent-productivity study.

1. **Is the main idea merely another action helper?** The implemented coordinator
   is exactly a small mechanism helper. A leap would require the unimplemented
   contract/presentation/session combination to remove repeated work across
   complete tasks. The report does not call the helper the finished capability.
2. **Is this original?** No. Ash, React-admin and headless controllers establish
   much of the pattern. Nisli's opportunity is combining domain operations with
   its existing semantic presentation and runtime in an incremental TypeScript
   layer. No uniqueness or superiority claim follows.
3. **Did the census measure boilerplate?** No. It counted syntax with exact
   callsites. Many signals, validators, transformations and outcome messages encode
   intended app behavior. A later ablation must count net shared/adapter code and
   removed author decisions, not all occurrences as savings.
4. **Does one Ledger app establish a general framework need?** No. Repeated
   editing patterns support investigation; the view/flow sub-bets have narrower
   local coverage. Held-out tasks and a second app are required before a universal
   authoring-model claim.
5. **Does Form falsification show a security vulnerability?** No. It uses internal
   headless draft entry points instead of UI controls and does not call the server.
   It disproves reuse as a complete trusted-operation contract. Production server
   validation and ownership rules are separate and must remain authoritative.
6. **Are the coordinator tests full equivalence tests?** No. They preserve ordered
   dependency-call traces under deterministic fixtures; Promise.allSettled can
   change timing versus the original Promise.all. They intentionally improve
   failure reporting by retaining the primary failure and acknowledgements.
   Simultaneous failure precedence, network races, authorization, browser
   interaction, independent sessions, durable idempotency and UI error binding are
   not proven.
7. **Does an execute rejection prove no effect occurred?** No. The first local
   prototype used a Boolean, which was corrected before final recording to
   not-started/unconfirmed/acknowledged. A lost response can follow a committed
   remote write. No automatic write retry or exactly-once claim is made.
8. **Can core already solve the import race?** Yes: resource passes the isolated
   latest-wins test. The case supports composing existing guarantees into app
   lifetimes, not adding another async primitive. Full import UI integration and
   rapid onChange/file-reselection behavior remain untested by this probe.
9. **Does keeping legacy APIs available prove the new path loses nothing?** It
   preserves the old path, not full new-path parity. Conditional/dependent fields,
   custom UI, provenance, offline semantics, routing and real-browser behavior
   remain explicit integration gates. Unsupported behavior cannot silently fall
   through or get removed from tests.
10. **Can schemas generate every useful surface?** No. Input parsing, authorization,
    presentation metadata, draft conversion and domain policy have distinct jobs.
    Standard Schema does not imply UI introspection or lossless JSON Schema
    conversion. Public tool export must be explicit and use the same authoritative
    operation boundary.
11. **Does this repeat the failed nextgen program?** It could. The next step is
    a complete application-task ablation with independent behavior assertions,
    not more vocabulary/checker work. Kill the bet if task authoring does not
    improve over today's engine or if domain capabilities are narrowed.

Final evidence: unchanged Ledger baseline 190 tests/no type errors; coordinator
15 passes; Form-as-operation 3 failures/1 control pass; import lifetime 1 failure/
1 existing-resource pass. No production edit, peer benchmark, real-server test,
new-layer end-to-end screen proof or measured agent improvement is claimed.
