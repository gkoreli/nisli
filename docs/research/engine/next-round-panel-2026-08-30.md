## Winner: reachability (ADR 0042) — why it beats the runner-up

- **"Nail existing capabilities until they make sense":** 0040 says "anything that floats is a layer" and "the engine owns focus and ARIA". The App bar-mode menu (every viewport < 792, so every phone) is not a layer: no Escape, no outside dismiss, no focus move/return. Sortable `th` has a click handler and `aria-sort` but no `tabindex`/keydown. `notify('negative')` is `aria-live="polite"` with a click-only `div` dismiss. `<label for>` points at a `radiogroup` div. These are the engine *not keeping* its own contract; nothing new is added.
- **Composition over inheritance / decompose freely:** the fix for the menu is to compose the existing overlay domain (`engine/overlay.ts`, `LayerKind`) instead of a hand-rolled sticky sheet — net code removal in `app.ts`, and a second real consumer of the layer stack besides Dialog/Dropdown, which is the evidence 0040's plan wanted.
- **Drastically better, minimally:** skin-contrast is values; reachability changes what a keyboard/AT/phone user can do at all. Vocabulary is author-felt.
- **Ledger dogfoods with zero edits:** all nine screens change behaviour on phone widths and for keyboard users; `transactions.ts` (four sortable columns) and every `notify` site are the proof surface. No file in `packages/ledger` moves, so the concurrent Ledger session is untouched.

### Candidate A: `skin-contrast` — contrast held by construction, proven like completeness

**What is wrong (measured, WCAG 2.x luminance, `skin/default.ts:833-855, 876-928`):**

| part on ground | light | dark | requirement |
|---|---|---|---|
| `notice.positive` `#fff` on `positive` | 5.02 | **2.22** | 4.5 (14px) |
| `notice.warning` `#fff` on `warning` | **3.64** | **1.95** | 4.5 |
| `notice.negative` `#fff` on `negative` | 5.44 | **2.78** | 4.5 |
| `text.faint` on `raised` (hints, "Updating…", 12px) | **3.45** | **3.87** | 4.5 |
| `tone.warning` on `raised` (Stat delta, 12px) | **3.64** | 7.97 | 4.5 |
| `input` border on `raised` (1.4.11 non-text) | **1.41** | **1.18** | 3.0 |
| `text.muted`, `tone.positive/negative`, primary button, link | pass | pass | — |

Root cause: `partsOf()` hard-codes `color: '#ffffff'` for the three tinted notices (`default.ts:927-929`) while the dark palette's tones are deliberately pastel; and the palette's `textFaint`/`warning`/`border` were chosen by eye. `skin.test.ts` proves completeness, no-layout, and scheme flip (`:79,83,92`) — never a contrast bound. The audit's "contrast held by construction" (§5) and the north star's N640 survivor were never carried into `@nisli/engine`.

**User-felt in Ledger:** every `notify(..., 'positive')` — budget saved, rule added, sync result, "Live data ready" (`budgets.ts:169`, `rules.ts:809`, `connections.ts:247-306`) — is at 2.2:1 in dark mode, which is Goga's phone at night; every Stat `hint` and form field `hint` (`accounts.ts:65`, `import.ts:480`, `transaction-dialog.ts` category hint) is sub-AA at 12px in light mode; every input's edge is barely distinguishable from its card in both schemes.

**Scores.** (1) Fidelity **5/5** — pure uplift of the skin/axes capability, no new part, no new word; the fix is palette values plus a derived ink (`noticeText` chosen from the notice ground), exactly 0035's "contrast by construction". (2) Severity **4/5** — measured, reproducible, hits the most frequent feedback channel in the app, in the scheme the phone uses; nobody filed it because nobody could see it in happy-dom. (3) Leverage **4/5** — adds the one missing proof to the skin contract (`PARTS` completeness × schemes × a contrast floor per text-part/ground pairing); makes "a skin never lies" checkable for third-party skins too; forces the engine to say which grounds a part may sit on, which is real ubiquitous-language work. (4) Dogfood **4/5** — zero Ledger edits; every screen changes on the phone at night; the verify is a person opening dark mode once. (5) Risk/size **5/5** — ~40 LOC palette + ~60 LOC `skin.test.ts` (a pure luminance function; no browser); the only risk is taste, and the floor is a number. (6) Bookkeeping **3/5** — amend 0035 §Completeness contract with the contrast clause; CHANGELOG 0.5.x; README "complete skin" paragraph; no new ADR needed.

**Verdict.** The cheapest, most provable, most owner-rule-faithful round on the table and the only one whose defect is measured today. **Round shape:** phase 0 — record the table above as an issue; phase 1 — add `contrastOf(part, ground)` proof to `skin.test.ts` over both schemes for every text-bearing part × the grounds it is placed on (derive the pairs from the blocks' `ctx.part` calls the way the scan derives parts), red first; phase 2 — fix the palettes (derive notice ink from the notice ground; raise `textFaint`, `warning`, `border`); phase 3 — 0035 amendment. **Gate:** skin test green in both schemes, `kernel.test` scan unchanged, a person checks dark notices on the phone. **Strongest argument against:** it is a skin-values round, and the owner's rules are about the engine; if the four unseen candidates include a "skin/appearance" one, fold this in rather than run it alone.

### Candidate B: `reachability` — every engine decision reachable by keyboard and AT

0040 says the engine owns "focus and ARIA" and that "anything that floats is a layer"; three things the engine draws break that today, and none is covered by the overlay tests.

**Defects (file:line):**
1. **App menu is not a layer.** The bar-mode nav sheet (`app.ts:262-273`) — the shell Ledger gets on every viewport < 792 (`shellMode`: 232 + 560), so at 768 and on every phone — is `position: sticky` in flow, not on the overlay stack: no Escape, no outside-pointer dismiss, no focus move into it, no focus return, and it pushes content down instead of floating. `layout.test.ts:35-43` tests sidebar/bar only; no test opens the menu.
2. **Sortable headers are unreachable by keyboard.** `th` gets `cursor: pointer` and a click handler (`table.ts:580-586`) but no `tabindex`, no `role="button"`, no keydown; `aria-sort` is announced but cannot be changed. Used by the transactions screen (`transactions.ts` four `sortable: true` columns).
3. **Notices are click-only and polite for errors.** `notify()` region is `role="status" aria-live="polite"` for every tone, including the `negative` rejections `busy.run` files (`notice.ts:91-92`, `status.ts:49,53`); dismiss is a bare `click` on a `div` (`notice.ts:112`) — not focusable, not keyboard-dismissable; the 4 s/8 s timers never pause on hover/focus. `extras.test.ts:103` proves "polite" as if it were the rule.
4. **Field label points at a `div`.** For a segmented select, `<label for="f-x">` targets the `role="radiogroup"` div (`form.ts:277-281,297`), which is not labelable — the label click does nothing; and a checkbox's visible caption is its `placeholder` (`form.ts:206`, `import.ts:496-497`, `transactions.ts` "Only uncategorized").
5. **Selectable rows** are focusable `tr` with Enter (`table.ts:533-537`) but carry no role/name for AT — a row reads as data, not as an action.

**Scores.** (1) Fidelity **5/5** — every fix is the engine keeping a guarantee it already claims (0040 keyboard model, README "focus and ARIA"); the App menu becoming a `popover` layer is the existing `ctx.overlay` behaviour applied to the one floating thing that skipped it; no new intent word. (2) Severity **3/5** — keyboard/AT users and, for #1, every phone user (the "sheet" that pushes content and cannot be escaped); but the app has one user who mostly uses a pointer, and no report exists. (3) Leverage **4/5** — removes the last floating thing outside the stack (App menu), so "everything that floats is a layer" becomes true rather than mostly true; makes `focusables()`/`escapeTarget` the single keyboard model; sort-as-button and row-as-action are decisions in `table.ts` with no new prop. (4) Dogfood **4/5** — zero Ledger edits; changes behaviour on every screen at bar width, on transactions sorting, on every notice. (5) Risk/size **3/5** — ~150–200 LOC across `app.ts`, `table.ts`, `notice.ts`, `form.ts` + tests in `overlay.test.ts`/`layout.test.ts`/`table.test.ts`/`extras.test.ts` (all happy-dom, no harness attestation needed); the risk is the App-menu-as-popover interaction with the sticky `header` z-order and `restoreFocus` — the overlay stack already models it. (6) Bookkeeping **3/5** — amend 0040's layer table (App menu row), README §Overlays and §Blocks; CHANGELOG; the agent skill's "what the engine guarantees" list.

**Verdict.** A real gap: the engine promises the keyboard model and delivers it for Dialog, Toolbar menu and confirm only. Likely partial overlap with an unseen "App at 768 / overlay" candidate; if so, merge #1 there and keep #2–#5 as the round. **Round shape:** issue first (the five items above); App menu → `ctx.overlay({ kind: 'popover', anchor: trigger })`; `th[sortable]` → `role="button" tabindex=0` Enter/Space; notices → `role="alert"` for negative, a focusable dismiss, timer pauses while hovered/focused; label/for → the first radio, checkbox caption from `label` not `placeholder`; rows → `role="button"`-equivalent naming. **Gate:** one test per item, the overlay stack test extended with the App menu, `pnpm -r typecheck`. **Strongest argument against:** it is five small fixes, not one drastic simplification — "minimal but drastically better" argues for landing them inside other rounds (menu in overlay work, label/caption in `vocabulary-contract`) rather than as a headline.

### Candidate C: `grid-balance` — Grid decides count, never shape; the orphan Stat

**Defect.** `columnsFor` (`engine/columns.ts:5-9`) returns `min(count, floor((w+gap)/(min+gap)))` and Grid renders `repeat(n, 1fr)` (`grid.ts:292-296`). Page content is capped at 1120 with 16 px padding → 1088 inner → **4 columns at every desktop width**; Overview has **5** Stats (`overview.ts:667-678`), so the "Savings rate" tile sits alone on a second row, full-width, at every width ≥ ~1176 — the first thing on the first screen. In the sidebar band 792–1119 the content column is 528–855 → 3 columns, so Account (4 Stats), Connections (4), Import (3+preview) each leave an orphan. `layout.test.ts:54` proves "one on a phone, four on a desktop, never more than there are cells" — count, not shape. The Stat itself has a flat hierarchy below the value: `delta` and `hint` are both 12 px muted (`stat.ts:334-339`, `default.ts:877-878`), distinguishable only by tone colour — which Candidate A shows is sub-AA for `warning`.

**Scores.** (1) Fidelity **4/5** — a better decision in an existing pure function, provable with numbers (`space.ts` doctrine); no new prop. Deduct one because "balanced rows" needs a stated rule (e.g. never leave one orphan when `count` can split evenly at ≥ `minColumn`; a last-row cell may span), and a rule about what a cell may do is a small vocabulary addition. (2) Severity **3/5** — seen by the user on the landing screen every day, but it is layout ugliness, not a failure. (3) Leverage **3/5** — the same rule serves Form (`form.ts:114` uses `columnsFor` too: 7 fields in the transaction dialog at 2 columns → a 1-field last row) and any future Grid; it is exactly "the engine decides what a person would decide by eye". (4) Dogfood **4/5** — zero Ledger edits; Overview, Account, Connections, Import, and the transaction dialog all change; the verify is a glance. (5) Risk/size **4/5** — ~30 LOC in `columns.ts` + `grid.ts` host, ~40 LOC tests (`columns.test.ts` exists); the risk is taste, mitigated by writing the rule first. (6) Bookkeeping **3/5** — a decision-rule line in 0038 §Space domain, README §How a block is built item 3, CHANGELOG.

**Verdict.** Small, visible, and the purest "engine, not author, decides" example in the list — but it is a taste rule; it earns a round only bundled with other `space.ts` decision fixes (the Toolbar "primary never leaves" defect from `vocabulary-contract` is the same shape). **Strongest argument against:** the north star's own evidence says aesthetics is not measurable, and "balanced" is closer to taste than "fits"; without a stated pure rule this becomes the author's eye moved into the engine, which is the thing 0034 warns against.

## Evaluation — vocabulary-contract

**Candidate: authoring-ergonomics (kernel API refactor for block authors, zero app-visible change)**

**(1) Fidelity to north star / owner rules — 3/5**
- It is uplift of an existing capability, not a disguised new one: `block()`/`Ctx` (kernel.ts:65-130) exists, every block is on it (kernel.test.ts:214-223 scan), and the candidate changes only how maintainers write blocks. Passes "no NEW capabilities" cleanly.
- But the north star (NORTH-STAR.md "The promise") and the audit (AUDIT §1: velocity *for agents building apps*, §4 item 5 "velocity was never a kill criterion") are about the **app author's** surface, which Ledger already shows is clean (overview.ts:2 imports 10 blocks, 1,149 LOC across 10 screens, zero style/el/html usage — grep count 4). Block-author ergonomics is one layer inward; the owner rule "nail existing ones until they make a lot of sense" fits, "drastically better" does not obviously — the engine has 15 blocks and ADR 0038 long-term plan §3 freezes the vocabulary at 15, so the beneficiary set is small.
- The candidate's own premise is partly stale: ADR 0038 Consequences records "spec.host(ctx) does not see props … skeleton() receives neither props nor ctx" as next-round gaps, yet `Ctx.props` already exists (kernel.ts:97-98) and `Statish.skeleton` reads `ctx.props.value` (kernel.test.ts:553). Part of the ergonomics debt was already paid inside the 0040 round without an ADR line.

**(2) Severity of user-felt defects — 1/5**
- By definition zero app-visible change. No open issue is an ergonomics issue: 0023 (dialog action row) and 0024 (prove parked) are behaviour/proof gaps. The `<each-item>` wrapper leak (form.test.ts:199-200 `[...grid(e).children].map(w => w.firstElementChild)`, layout.test.ts:87) is a *test-author* nuisance from `@nisli/core`'s `each()`, not a rendering defect; a user never sees it. The `as Content` cast (app.ts:114) and `Content = TemplateResult | { __type: 'factory' }` (types.ts:4) are typing warts from core issue 0021's fix, also invisible.
- LOC "grew in 0038": CHANGELOG 0.3.0 table shows blocks 1,476 → 1,725 (+249) of which kernel.ts is 224; per-block deltas are ±10 except form.ts 358→370. The verbosity is real but modest: `ctx.part([], {...})` (structure-only, no look) appears 24 times across blocks (form.ts 8, columns.ts 4, table.ts 3), and form.ts has 17 `ctx.part(` calls, often with a `(): Parts =>` thunk (form.ts:262-265). That is ceremony, not a defect anyone feels.

**(3) Architectural leverage — 3/5**
- DDD fit is good: the kernel is already "composition over inheritance" (ADR 0038 "Design principles applied", kernel.ts:12-15) and every visual path runs through one function. A terser structure declaration (e.g. a `ctx.box(structure)` for the 24 look-less `part([], …)` sites, a typed `Rendered`/`Content` unification so `toList()` (types.ts:21) and the `as Content` cast disappear, an `each` test helper that unwraps `<each-item>`) would *simplify*, not add structure.
- What it unblocks: little directly. The density/input axes (0034 plan §5, 0038 plan §1) go through `ctx.metrics` and trailing `layout` params, which already exist. `prove()` un-parking (issue 0024) depends on `reportIf`/`mount()`, already in place. The only concrete unblock is the each-item leak, and that is really a core `each()` question (should `each()` expose its items without a `display:contents` wrapper, or should `mount()` hide it?) — arguably scope creep into `@nisli/core`.

**(4) Dogfood value in Ledger — 1/5**
- Zero screens change behaviour; the acceptance test is "Ledger with zero edits" exactly as in ADR 0038 Consequences and ADR 0040 Acceptance. That is a regression gate, not dogfooding: Ledger cannot *discover* anything about kernel ergonomics because it never touches `block()`. Ledger is currently being edited by another session (`git status`: store.ts, store.test.ts, seed.ts deleted, initial-ledger.ts new) — irrelevant to this round since it needs no Ledger edit, which is also the tell that the owner rule "Ledger dogfoods every engine change" is satisfied only vacuously.

**(5) Risk and size — 3/5**
- Size: kernel.ts 500 lines (of which ~280 is overlay manager, untouched), 19 block files ~1,500 LOC, every one of which would be re-touched for a `part()` signature change; tests 151+ pass through `mount()` and the kernel scan (kernel.test.ts:203-211) which must be extended for any new door. A full rewrite of `part()`/`Rendered`/`Content` touches roughly 1,700–2,000 LOC across 25 files — the same blast radius as the 0038 migration, for a fraction of its payoff.
- Risk is low semantically (types + tests + scan catch drift; Ledger typecheck is the outer gate) but high in *churn-to-value*: the third consecutive all-blocks sweep (0038 kernel, 0040 overlay) in a week.

**(6) Bookkeeping impact — 2/5**
- Would need an ADR (0042) amending 0038's Ctx contract, a CHANGELOG 0.5.0 with a new LOC table (0038 promised "the whole-tree delta … recorded in CHANGELOG"; keeping that ledger is the honest accounting for a LOC-motivated round), README "How a block is built" rewrite (README.md:60+), and closing the 0038 gap note on `host(ctx, props)`/`skeleton(ctx, props)` that is already silently resolved. No issue to close. Bookkeeping is proportionate but nothing outside the engine package learns anything.

**Verdict.** This is a legitimate, rule-compliant polish of an existing capability with good DDD hygiene, but it is the weakest kind of "drastically better": it optimises the experience of the ~15-block engine's own maintainers, whom the audit never identified as the velocity bottleneck, fixes nothing a user feels, gives Ledger nothing to dogfood, and re-sweeps every block file for the third time in a week. The specific complaints are real but small (24 look-less `part([], …)` calls, one `as Content` cast, `toList()` in five blocks, an `<each-item>` unwrap in two tests, a +249 LOC that is 90% the kernel itself), and half the recorded gap (`host`/`skeleton` seeing props) has already been absorbed. Better folded as a bounded "kernel API tidy" phase inside a round that has user-visible payoff (e.g. the dialog action row of issue 0023 as a `fitRow` behaviour, or un-parking `prove()` now that ADR 0041 lands), where the ergonomics change is exercised by writing one new behaviour rather than by rewriting fifteen old ones.

**Proposed round shape (if taken).** Phase 0: measure — list every `ctx.part([], …)`, `toList`, `as Content`, thunk-typed `Parts`, and each-item unwrap site (numbers above) and write the target API in ADR 0042 before code. Phase 1: kernel only — add `ctx.box(structure)` (or make `parts` optional), unify `Rendered`/`Content`/`Children` in types.ts, add a `mount().items(selector)` helper that hides `<each-item>`; extend kernel.test.ts scan with a rule banning `part([]`. Phase 2: migrate blocks in two batches (layout blocks; form/table/toolbar), each batch a commit with the LOC table row. **Single strongest argument against doing it now.** The round's rule is "nail existing capabilities until they make a lot of sense", and the capability that does not yet make sense is the *Decision* context at width — `prove()` parked (0024), the estimator uncalibrated, the dialog action row missing (0023). A second axis doubles the context matrix (widths × input) that the engine must decide correctly in, and does so precisely where the engine is still blind: nothing but `mount()` can observe a touch layout, and the only judge is a thumb on a phone. Adding a dimension to an unproven decision space before the proof harness works is the same "measure what can be measured tonight" drift the audit (AUDIT-2026-08-27.md §4) warns about, wearing a new coat.

## Evaluation — authoring-ergonomics

**Candidate: app-navigation — evaluation**

**(1) Fidelity to north star / owner rules — 3/5**
- Uplift, genuinely: the phone menu sheet is the one floating thing 0040 left behind. `app.ts:101-112` renders it as `position: sticky; zIndex: metrics.layer.bar - 1` under the bar — not a `Layer`, not on the stack, no `ctx.overlay`. ADR 0040 "Long-term plan" §2 says an anchored non-trapping layer "is exactly what `useOverlay` already provides". Moving it onto `ctx.overlay({ kind: 'popover' })` is composition of an existing behaviour (0038/0040 principle), zero new vocabulary.
- Disguised new capability, two parts: (a) "breadcrumbs from the route tree" — there is no route tree. `@nisli/router` is a flat catalog (`grep children|parent|nested|tree packages/router/src/matcher.ts route.ts` → empty; `ledger/src/router.ts:6-16` is nine flat routes). Breadcrumbs need either router nesting (new router capability) or a `parent`/`crumbs` prop on `Page` (new word, home 3 in 0034). (b) "route-awareness beyond a location string" — `AppProps.location: string` (`app.ts:16`) is deliberately the only coupling; 0034's bounded-context table puts the Router in the **Application** context, and the engine importing `@nisli/router` would invert `Intent → Decision → Appearance`. Any richer route object must arrive as data through props, or it violates the dependency rule.
- Skip link, landmarks, focus-on-navigation are uplift of App/Page's existing responsibility ("the shell").

**(2) Severity of defects an agent cannot see but a user feels — 3/5**
- Phone menu (Ledger README §"Private phone access" makes phone a first-class context): open it and there is no Escape, no outside-tap dismiss, no focus move, focus never returns; the toggle has `aria-expanded` but no `aria-controls` (`app.ts:92-98`); the sheet pushes content down instead of floating. Only the `location` effect closes it (`app.ts:43`). This is the same class of defect 0040 fixed for dialogs, milder.
- Landmark exposure: two `<nav aria-label="Primary">` (`app.ts:60`, `app.ts:101`); in bar mode with the menu closed **both** are `display:none`, so a screen-reader user on a phone has no navigation landmark at all.
- No skip link: keyboard users tab through brand + 8 nav links (`ledger/router.ts:18-27`) on every screen at desktop width. The router already offers the target (`application.ts:20-27` `outletAttrs.id` "e.g. for a skip link"); nobody wires it (`ledger/router.ts:6` passes no options).
- Document title never changes: routes define no `title`, `dev/index.html` says `Ledger`, router reconciles `document.title = metadata?.title ?? defaultTitle` on every navigation (`router.ts:459-461`). Every tab and every SR page announcement says "Ledger". `Page` knows the title (`page.ts:8`) and does nothing with it.
- Heading outline: no `h1` anywhere — page title is `h2` (`toolbar.ts:112`), section `h3` (`section.ts:21`), dialog `h2` (`dialog.ts:71`), brand a `div` (`app.ts:76,91`).
- Focus on navigation is already correct: router focuses the outlet on push (`router.ts:516-519`) — not a defect, so that item of the candidate is empty.
- Nothing here is a layout-at-width defect; sighted mouse users feel only the menu. Lower than 0040's "every open dialog closed on one Escape".

**(3) Architectural leverage — 3/5**
- Adds structure cheaply for the menu: one `ctx.overlay` call, `z` from `metrics.layer.popover`, kernel scan rules 6/7 already forbid a hand-rolled listener, so the fifth overlay cannot decide alone.
- Dangerous coupling on landmarks: the `main` landmark is **owned by the router outlet** (`application.ts:80-87` sets `role=main tabindex=-1`, "cannot be overridden"), and the kernel's `restoreTarget` (`kernel.ts:419-424`) finds it by `closest('main,[role=main]')` — the engine's focus-restore works in Ledger by coincidence of composition. If App wraps content in its own `<main>` you get nested main landmarks; if the engine writes `document.title` from `Page.title`, the router overwrites it on the next navigation (`router.ts:461`). The round must *decide the seam* (engine derives the skip target from the `[role=main]` it finds inside `content` — home 1, derived from structure; title stays route metadata) or it adds a second owner for each.
- DDD fit: a "Navigation" sub-domain inside Blocks is plausible (App, Page, Link, the menu layer), but it has no pure decision vocabulary to extract the way Space/Overlay did — most of it is markup, not decisions. Unblocks little: not density/input axes, not `prove()` (0024), not the fit solver the audit §5 named as the centre.

**(4) Dogfood value in Ledger — 3/5**
- Zero-edit behaviour change (the 0040 acceptance pattern): menu sheet, skip link, landmark exposure change every screen's shell without touching `ledger/src`. `main.ts:14-19` is the only App call.
- Document title needs Ledger edits (route `title` in `router.ts`) — a Ledger change, and another session has `store.ts`/`seed.ts` in flight (`git status`). Breadcrumbs would change only `account.ts` (the one child route, `/accounts/:id`; it has no back link today) — 1 of 9 screens, and it needs Ledger edits. Ledger's IA is too flat to dogfood breadcrumbs honestly.

**(5) Risk and size — 4/5 (small, low risk)**
- Surface: `app.ts` 117 lines, `page.ts` 48; `kernel.ts` overlay manager untouched. Estimate 150–250 LOC net including tests; App has 3 tests in `layout.test.ts:31-48`, the menu proof goes in `blocks/overlay.test.ts` via `mount()` at 360.
- Review gate: kernel scan (`kernel.test.ts` rules 1–7), the 0040 proof style (Escape routing, focus return to the Menu button, outside pointer, Tab leaves), Ledger typechecks + 38 tests with zero edits. Real risk is only the router/engine seam above; a wrong call there creates duplicate landmarks or a title race that no unit test in the engine alone catches.

**(6) Bookkeeping impact — 3/5**
- Needs one ADR (0042 — App shell navigation: the menu as a popover layer, the landmark/skip-link seam with the router, heading outline decision) plus an amendment note in 0040's consumer table; a CHANGELOG 0.5.0 entry; issues for the deferred items (breadcrumbs pending a route tree; document title as route metadata for Ledger). The seam decision must be recorded in *both* the engine ADR and a router note, or the next round re-argues who owns `main`.

**Verdict.** Roughly half of this candidate is honest uplift — the phone menu as a `popover` layer, an exposed navigation landmark in bar mode, a skip link derived from the `[role=main]` the App finds inside its content — small, zero-Ledger-edit, provable through `mount()`, and it closes the one overlay 0040 left out. The other half (breadcrumbs, "route-awareness", document title, focus on navigation) is either already done by the router, a coupling the 0034 dependency rule forbids, or a new capability the flat router cannot supply and Ledger's flat IA would not exercise. Scoped down, it is a good half-round; at full scope it is disguised new capability wearing an a11y coat.

**Proposed round shape.** Phase A (engine, ~1 day): menu sheet → `ctx.overlay({ kind: 'popover', anchor: Menu button, within: sheet })`, `aria-controls` on the toggle, sheet floats at `metrics.layer.popover` instead of pushing content; proofs in `blocks/overlay.test.ts` at 360 (Escape → closed + focus on Menu; outside pointer → closed; navigation → closed; Tab leaves). Phase B (engine, ~half day): one `<nav>` element whose display flips by mode rather than two; skip link rendered by App to the first `[role=main]` found in `content` at mount, hidden until focused (a skin part `nav.skip`), no link when none is found; record the seam: the router owns `main`, `tabindex`, focus and `document.title`; the engine never writes them. Phase C (Ledger, after the concurrent session lands, ~1 hour): route `title`s in `router.ts`. Deferred to issues: breadcrumbs (blocked on a route tree), `h1`. Review gate: kernel scan green, 0040-style keyboard proof, Ledger zero-edit typecheck + tests, ADR 0042 + 0040 amendment + CHANGELOG in the same PR. Acceptance: at 360 in Ledger, Menu → Escape closes and focus is on Menu; tap outside closes; at 1280 the first Tab reveals "Skip to content" and Enter lands focus on the router outlet; no Ledger source file changed for A/B.

**Strongest argument against doing it now.** The audit (§5) says the thing to grow is the fit solver — "the only code that decides across siblings" — and `prove()` is still parked (issue 0024); this round spends its budget on shell a11y that renders correctly today and decides nothing at width, while the router already handles focus-on-navigation and the parts that would carry real leverage (breadcrumbs, route awareness) require capabilities that do not exist and would be added under an "uplift" label.

### Scores

**(1) Fidelity to north star / owner rules — 5/5.** This is pure uplift of the existing capability the audit said survives ("the words are right", AUDIT §5) and that ADR 0034 names as its first bounded context (**Intent** = `blocks/types.ts` + the prop types). No new block, no new axis, no new decision. It directly enforces 0034's own rule that app code may only say meaning — `role: 'muted'` is today a per-instance appearance prop wearing a semantic name, the exact "home 3 erodes the contract" case 0034 argues against. Not a disguised capability; the risk is the opposite (that it stays cosmetic).

**(2) Severity of user-felt defects — 3/5.** Most of this is agent/author-felt (wrong word compiles, wrong Action field silently ignored). Two are user-felt: (a) a Toolbar primary *can* leave into the menu contrary to every document (`toolbar.ts:52`) — reachable only below ~250 px so rare in Ledger; (b) `Empty.action` renders a destructive action as a primary button — no Ledger site does this today (`connections.ts:188` is a plain primary). The `Table.empty` string vs `Empty` block gap means Ledger's empty tables cannot offer "Add …" where the user is looking (`account.ts:39`, `budgets.ts:54`, `rules.ts:89-93`), which is a real UX flatness. Agent-felt severity is high (three `key`s), but the brief asks what a user feels.

**(3) Architectural leverage — 4/5.** DDD fit is exact: this is the ubiquitous-language pass 0034 started and 0037/0038/0040 each extended with their own tables, never reconciled (0037's `Field.key`, 0040's `Kind`). Concrete simplifications it unlocks: one `Action` honoured identically by Toolbar/Empty/Form/Confirm/Dialog (which is issue 0023 option 1 for free, or its precondition); `Text.role` losing `muted` forces the engine to *decide* mutedness from structure (Stat delta, Table fold line, notice already do this via parts) — a home-1 move; `Table.empty: string | EmptyProps` reuses the existing block; `kind` split into datum-kind (Column/Field share `text|number|money|date`) and control-kind removes the 0037 rule-4 apology. It reduces surface rather than adding. Not 5 because none of it changes a decision rule in `engine/space.ts`; leverage is on the boundary, not the core.

**(4) Dogfood value in Ledger — 4/5, but it *requires* Ledger edits and another session is in Ledger.** Behaviour changes by screen: `account/budgets/rules/overview/transactions/connections` tables (empty-state with action; primary-never-leaves at narrow widths); `connections.ts:216` fieldless Form → real actions; `connections.ts:161` destructive tertiary behaves the same everywhere. Migration touches every screen because of `key` (44 sites) and `role: 'muted'` (8 sites) — and Ledger's working tree is currently dirty in `src/data/*` and `server/*` (git status). A rename round *cannot* avoid the screens directory, so it must be sequenced behind or coordinated with that session; the screens files themselves are clean right now, which is the window.

**(5) Risk and size — 3/5.** Engine: `types.ts`, 12 block prop interfaces, `schema.ts`, `toolbar.ts:52`, `empty.ts`, `form.ts:336-346`, `confirm.ts`, `table.ts` (empty), `text.ts` — est. 150–250 LOC engine + tests; plus `index.ts` re-exports, README (the `role: 'muted'` and "primary never leaves" claims), the agent skill (`SKILL.md`/`AGENTS.md`, 744 lines, dozens of mentions). Ledger: ~60 mechanical edits across 9 screens + `main.ts` (`content`→`children`). Risk is breaking-change churn on a 0.4.0 package with one consumer — acceptable; the real risk is scope creep ("while we're here, add Dialog actions"). Review gate: `kernel.test.ts` scan + `skin.test.ts` completeness already cover the look side; needs a new **vocabulary test** (a type-level test that each word has one type across blocks, and a 200-px Toolbar test for the primary) per the harness-attestation rule. No browser/lifecycle harness → no cleanup attestation needed beyond the vitest/dist gotcha.

**(6) Bookkeeping impact — 4/5 (heavy, mandatory).** A new ADR (0042 "Intent vocabulary contract") that *replaces* the four scattered ubiquitous-language tables with one and amends 0034 §The contract, 0037 §Ubiquitous language (`key`, `kind`), 0040 (`Kind`). Engine CHANGELOG 0.5.0 with a rename table; Ledger CHANGELOG entry; README rewrite of the contract paragraph; the agent skill must be regenerated (it currently documents the false "primary never leaves" for Toolbar at `SKILL.md:53`). Issue 0023 either closes or is re-scoped. This is a lot of prose for a small diff, which is appropriate here: the deliverable *is* the prose-plus-types.

### Verdict

This is the most owner-rule-faithful candidate imaginable — no new capability, pure DDD ubiquitous-language work on the one bounded context every other ADR depends on — and the evidence shows the contract is genuinely broken, not just untidy: three `key`s, a `kind` that leaks control shape, a `role` that is a colour in disguise and accounts for 80 % of its own use, an `Action` type honoured by one block and silently half-ignored by three, and a documented "primary never leaves" that Toolbar does not implement. It is also small, fully provable in happy-dom, and touches every Ledger screen mechanically, which is exactly the dogfood shape the owner wants. Its weakness is that most of the pain is an author's pain, not a user's; the user-visible wins (empty tables with a real action, one Action row everywhere, the Toolbar primary guarantee) are modest and partly overlap issue 0023.

**Proposed round shape.** Phase 0 (bookkeeping first): draft ADR 0042 with the single vocabulary table — for each word: type, meaning, which blocks, optional/required, default — and the rename list; review the table before any code. Phase 1 (engine, one commit per word family): `key`→`rowKey`/`draftKey`/`name`(Field); `kind` split (`DataKind` shared by Column and Field; control-shape words become `Field.control?` or are derived — `textarea` from `long`, `checkbox` from a boolean datum); `Text.role` drops `muted` (engine derives it from placement, e.g. Stat/Empty already do) and becomes `Text.kind`/`role` reconciled with ARIA; `Action` honoured identically (priority + destructive) in Toolbar, Empty, Form, confirm — confirm takes an `Action`; `Toolbar` primaries `overflowable: false` + `FIT_ROW` report; `Table.empty` accepts `EmptyProps`; `App.content`→`children`; `text` formatter renamed `format`. Phase 2 (Ledger migration, coordinated with the other session — screens dir is clean now): mechanical rename, then delete the fieldless Form at `connections.ts:216`. Phase 3: README + skill regeneration, CHANGELOGs, ADR status flips. **Review gate:** a new `vocabulary.test.ts` (type-level: each word resolves to one type across all prop interfaces; runtime: Toolbar at 200 px keeps the primary and files `FIT_ROW`; Empty/Form/confirm render a destructive Action as `button.danger`), plus the existing kernel scan and skin completeness green, plus `pnpm -r typecheck` proving Ledger compiles with zero `as const` on tone/priority literals. **Acceptance test:** an agent given only the skill can write a new Ledger screen without producing any of the five "common mistakes" this round removes, and `grep -c "role: 'muted'\|fields: \[\]" packages/ledger/src` is 0.

**Strongest argument against doing it now.** The Proof round (0041) and the Ledger bank-connectivity work are both landing concurrently, and this round's payload is a rename sweep across all nine Ledger screens plus a 744-line agent skill — a merge-conflict magnet with low user-visible payoff, whose real defects (Toolbar primary at <250 px, Empty ignoring `destructive`) affect no Ledger screen today. Doing it first also means every later engine round re-litigates vocabulary once a genuine new decision (Dialog actions, density axis) shows what the words needed to mean; the honest sequencing is to land 0023 (which forces `Action` to be honoured in a fourth place) and let that collision *decide* the vocabulary, then run this round as the reconciliation with real evidence rather than a speculative rename.
