# AGENTS.md — nisli

## Repository shape

- This is a pnpm workspace with four independently versioned public packages:
  - `@nisli/core` in `packages/core`
  - `@nisli/router` in `packages/router`
  - `@nisli/ssg` in `packages/ssg`
  - `@nisli/ui` in `packages/ui`
- `packages/www` is the private nisli.dev application. It dogfoods core,
  router, SSG, and a complete copy of the UI registry.
- The root `package.json` is private and delegates workspace scripts.
- The npm README for core is `packages/core/README.md`. Keep its user-facing
  framework and ecosystem guidance aligned with the root `README.md`; the root
  may additionally contain repository development instructions.
- Package-specific usage belongs in each package README. Architecture decisions
  belong in `docs/adr`; temporary or evidentiary worklists belong under
  `docs/worklists/<area>`, never at the repository root or among package source.
- Deep framework authoring rules live in `.agents/skills/nisli-framework`.

## Commands

- `pnpm install`
- `pnpm build`
- `pnpm test`
- `pnpm typecheck`
- Use `pnpm --filter <package> <script>` for a focused package run, but finish
  cross-package changes with the relevant root gates.

## Worktree discipline

- This repo runs many agents in parallel git worktrees; each worktree has its
  own `node_modules`.
- Preserve unrelated local changes. Never edit another lane's worktree or
  generated output to work around a failure.
- After rebasing or fast-forwarding past a change that adds a workspace package
  or dependency, run `pnpm install` before trusting red tests/typecheck.
  `Cannot find module @nisli/…` after such a rebase is usually a stale install.
- “Gates green” includes remote CI green on `main` after push. The pusher watches
  the run with `gh run list` / `gh run watch`; local success alone is not done.
  A known-blocked job must skip loudly with a reason, never remain red as normal.

## Core framework work

- Use `.agents/skills/nisli-framework` when writing, reviewing, or debugging
  Nisli components.
- Component setup is synchronous. Capture services, contexts, effects, and
  lifecycle hooks during setup; perform async work from captured closures.
- In Nisli templates, compose custom elements through the typed factory returned
  by `component()`. Plain `<ui-*>` markup remains an intentional public
  consumption path for `@nisli/ui` and other standards-facing HTML consumers.
- Prefer the current core primitives over registry-local substitutes:
  - `children(fallback?)` for the single default projection slot
  - `component(..., { attrs })` for live string/boolean/number/forwarded attrs
  - `createContext` for subtree-scoped, portal-safe component-family state
  - `el()` only when the native HTML tag name is selected at runtime
  - `each()` for reactive keyed lists
  - `resource()` for local async derivations without query-cache policy
- App services use global `inject` / `provide`; parent-descendant state uses
  `createContext`. Do not conflate the two scopes.
- Tests live beside source in `packages/core/src` and run under happy-dom.
  Prefer public APIs (`signal`, `component`, `html`, `inject`, `query`, etc.).
- Keep `index.ts` files as barrel exports only. Do not hand-edit `dist`; it is
  generated by `pnpm build`.

## Package architecture

- Development exports point at TypeScript source. Published exports point at
  built files through `publishConfig`.
- `@nisli/core` owns component authoring and the browser runtime. It must stay
  free of runtime dependencies and static-build policy.
- `@nisli/router` owns the shared typed route contract:
  - the package root includes the browser outlet;
  - `@nisli/router/vite` supplies direct-route fallback;
  - `@nisli/router/catalog` is the environment-neutral, side-effect-free
    catalog/matcher surface for shared packages and Workers;
  - render-less route identity may be completed with typed `bindRenders()`.
- `@nisli/ssg` owns static rendering, route expansion, output helpers, and SSG
  build policy. Prefer passing the same application router used by browser and
  Vite rather than maintaining a second route table.
- `@nisli/ui` is a registry plus the `nisli-ui` CLI, not an importable runtime
  component library. Components ship as copyable source under `registry/`; only
  the CLI is compiled to `dist` (ADR 0022 and `packages/ui/NORTH-STAR.md`).
- `packages/www/src/nisli-ui` is derived by the real UI CLI. Change the registry
  first, then run the package sync/build workflow and commit the refreshed
  copies; do not treat site copies as the source of truth.

## UI registry work

- Preserve the source-first contract: copied files may depend on `@nisli/core`
  and other registry items, but must not acquire hidden runtime npm dependencies.
- Components use light DOM and layout-transparent hosts. Audit both hazards when
  porting upstream markup:
  - box-model/direct-child selectors must reach the painted descendant through
    the `display: contents` host;
  - native parent-child contracts (for example `fieldset`/`legend`) may require
    explicit semantic restoration.
- UI worklists and parity evidence live in `docs/worklists/ui/` (for example
  `UI-30-WORKLIST.md`, `UI-36A-WORKLIST.md`, and `UI-36B-WORKLIST.md`). Keep
  durable architecture in ADRs and current product status in
  `packages/ui/NORTH-STAR.md` and `packages/ui/CHANGELOG.md`.
- Registry tests live beside copied source under `packages/ui/registry`.
  Validate both typed factory use and plain-HTML attribute/children use when the
  component exposes both contracts.

## Publishing invariants

- Workflow: `.github/workflows/auto-tag.yml`.
- The matrix publishes core, router, SSG, and UI independently with tags
  `core-vX.Y.Z`, `router-vX.Y.Z`, `ssg-vX.Y.Z`, and `ui-vX.Y.Z`.
- npm Trusted Publisher must name `auto-tag.yml` for every public package.
- Keep Node `24` and `npm install -g npm@latest` for OIDC publishing.
- Build the tarball with `pnpm pack` so `publishConfig.exports` is applied, then
  publish that tarball with `npm publish *.tgz --provenance --access public`.
  Publishing the directory directly can ship development exports that point at
  excluded TypeScript source.
- Repository metadata must use `https://github.com/gkoreli/nisli.git` and the
  correct `packages/<name>` directory for all four public packages.

## Publishing failure pattern

- npm may return a misleading scoped-package `404 Not Found` on publish. This
  usually means a Trusted Publisher identity mismatch rather than a missing
  package.
- Check the workflow filename, package repository metadata, Node/npm versions,
  and that package's Trusted Publisher settings.
- The workflow creates the tag and GitHub release before npm publish. If publish
  fails after tag creation, delete that package-prefixed release/tag before
  retrying the same version:
  - `gh release delete <package>-vX.Y.Z --cleanup-tag --yes`

## Release checklist

- Bump only the intended `packages/<name>/package.json` and update its changelog.
- Confirm the exact version is free:
  - `npm view @nisli/<name>@X.Y.Z version`
  - `E404 No match found for version` means it is available.
- Run `pnpm build`, `pnpm test`, and `pnpm typecheck`.
- Push to `main` and watch the publish run:
  - `gh run list --workflow auto-tag.yml --limit 5`
  - `gh run watch <run-id> --exit-status`
- Confirm the package, version, and repository metadata on npm:
  - `npm view @nisli/<name> version repository --json`
